# 🤖 京东自动化平台 (JD UI Automation)

基于 **Appium + Flask** 的京东 Android App UI 自动化平台。Web 页面点击模块卡片，即可在后台运行自动化任务，实时查看执行日志。

## 架构

```
浏览器 (Web UI)           ← 模块卡片 + SSE 实时日志
     │ HTTP + SSE
Flask Web 服务器           ← 路由、任务调度、日志流
     │ 后台线程
模块系统 (BaseModule)      ← 自动发现、独立运行
     │ Appium WebDriver
Android 手机 (JD App)      ← 自动化执行目标
```

## 快速开始

### 环境要求

- Python 3.7+
- Node.js 16+
- Android 手机（已开启 USB 调试）
- [platform-tools (adb)](https://developer.android.com/studio/releases/platform-tools)

### 安装

```bash
# 1. 安装 uiautomator2 driver
npx appium driver install uiautomator2

# 2. 安装 Python 依赖
cd D:/AI_work/JDUItest
pip install -r requirements.txt
```

### 运行

```bash
# 终端1: 启动 Appium 服务
npx appium

# 终端2: 启动 Web 平台
python app.py
```

浏览器打开 [http://localhost:5000](http://localhost:5000)

#### Appium 常驻启动器（推荐）

`start_appium.cmd`（双击运行，窗口保持开启）：

- 自动用 `node + node_modules/appium/index.js` 拉起 Appium，**进程退出后 5 秒自动重启**；
- 每次启动前把 `adb devices` 结果写进日志，方便确认设备在线；
- 日志：`_appium_stdout.txt`。

> ⚠️ **设备一掉线，Appium 会自杀**。USB 短暂断开时 Appium 在清理 session 阶段执行
> `adb shell settings delete global hidden_api_policy...` 会报 `device not found`，
> `teen_process` 抛未捕获的 `adbExec` 异常，Node 进程直接 exit 1。
> 之后所有模块都会报「Appium 服务不可达」。用本启动器可自动恢复；
> 若仍失败，先 `adb devices` 确认设备是 `device` 而不是 `offline`。

#### Web 平台常驻启动器（推荐）

`start_platform.cmd`（双击运行，窗口保持开启）：用 `D:\Program Files\Python37\python.exe`
拉起 `app.py`，进程退出后 5 秒自动重启，日志写 `_flask_stdout.txt`。

> ⚠️ `config.FLASK_DEBUG=False`，**改完 `modules/*.py`、`utils/*.py`、`templates/*.html`
> 必须重启本启动器**，否则内存里跑的还是旧代码。

## 添加新模块

1. 在 `modules/` 下新建 `.py` 文件（文件名不要以 `_` 开头，且不能叫 `base.py`）
2. 继承 `BaseModule` 类
3. 设置 `name`、`description`、`icon` 类属性
4. 实现 `run(self, log, stop_event)` 方法；用 `log.write_log()` / `write_step()` / `done()` / `error()`
   输出 SSE 日志，循环里定期检查 `stop_event.is_set()`

自动发现注册，前端卡片由 `/api/modules` 动态渲染并自带【▶ 运行】按钮，**无需修改任何其他文件**。
但 `modules.get_modules()` 有进程内缓存、`FLASK_DEBUG=False` 下模板也有 Jinja 缓存：
**新增/改动模块或模板后必须重启 Flask**，浏览器侧再 `Ctrl+F5` 硬刷新（静态资源 URL 带 `?v=` 版本号）。

## 任务1【秒杀】完整流程

在 Web 页面点击「秒杀任务」卡片即可（等价于 `POST /api/run/秒杀任务`）：

1. **公共模块**（`utils/jd_ui.py` → `JDUI.to_all_channels`）：回到京东首页 → 金刚区左滑到第二页 → 点击【全部频道】
2. 点击【优惠权益】tab → 【秒杀】 → 【赚更多京豆】 → 【全部任务】弹窗
3. 逐个点击弹窗里的【去浏览】，每次停留 **16 秒** 后返回，直到列表里没有【去浏览】；弹窗一打开就没有【去浏览】时立即跳出，不空转
4. 点击弹窗第一条【去刮卡】→ 回到天天领豆页
5. **刮卡轮次**：反复点击【立即刮卡】，每张刮完左滑【任务卡】继续检查是否还有【立即刮卡】，直到没有为止
6. **刷新【天天领豆】**（返回上一页再重进）：若仍有【做任务解锁刮卡】，回到第 3 步再做一轮「浏览任务 + 刮卡」；直到刷新后不再出现【做任务解锁刮卡】

模块参数在 `modules/task1_seckill.py` 顶部：`BROWSE_SECONDS=16`、`MAX_ROUNDS=40`、`MAX_SCAN_SWIPES=2`、`MAX_CARD_ROUNDS=12`、`MAX_CARD_CLICKS=30`、`MAX_EMPTY_SWIPES=2`、`MAX_NO_CHANGE=2`。

### 实测约束（2026-11-10，1080×2340 / Appium 3.9 / uiautomator2 8.7.3）

- 京东的【全部频道】【优惠权益】【秒杀】【天天领豆】等 H5 页**不透出无障碍节点**，`contexts` 只有 `NATIVE_APP`、无 devtools socket。这些页面只能按标定坐标点击，坐标集中在 `utils/jd_ui.py` 的 `POINTS` / `SWIPES`，运行时按实际分辨率等比缩放。**换机型或京东改版需重新校准坐标**。
- 任务弹窗是原生节点，`text="去浏览"` / `"去刮卡"` / `"立即刮卡"` 可精确定位，循环终止条件据此判断。
- Appium 3.9 + Appium-Python-Client 2.11.1 下 `find_elements` 的 `-android uiautomator` 与 `xpath` 策略会报 `selector is not present in JSON`，因此统一采用「解析 `page_source` → 取 `bounds` → 坐标 `tap`」，不依赖元素定位。
- `utils/driver.py` 的 session 探活已改为 `page_source`；`current_package` / `current_activity` 在 Appium 3 下会抛 `UnknownMethodException`，会让 session 被反复重建。
- 点击【去浏览】偶发「京东验证」风控页，模块会自动点【快速验证】；若需要短信/人工验证会报错并保存现场截图。
- 失败时自动截图到 `debug_shots/`，便于校准坐标。

### 导航稳定性修复（2026-11-10 复测）

- **任务开始前必须冷启动京东**：`config.py` 用 `noReset=True`，Appium 不会重启 App。若京东停在「秒送」tab 或首页已滚到推荐流，金刚区不在视口，左滑会被外层 ViewPager 吃掉并切成「秒送」页，`【全部频道】` 永远找不到。`JDUI.to_all_channels()` 现在会先 `adb force-stop` + 重新拉起，保证每次从干净的「首页」tab 顶部开始（每个 JDUI 实例只做一次）。
- **H5 坐标点击统一走 `adb shell input tap`**（`JDUI.tap()` → `adb_tap()`）：Appium 3 的 W3C `tap` 在京东 H5 页偶发被吞，表现为点了但页面没反应；原生注入实测稳定。`swipe` / `back` / 弹窗节点点击不受影响。
- **【全部频道】页默认停在「生活服务」tab**：必须先点【优惠权益】tab `(407,765)`，网格才会变成以【秒杀】为首项，再点 `(153,530)` 进入京东秒杀页。两个坐标在 1080×2340 下实测正确（调试时注意 IDE 里显示的截图是缩略图，肉眼读数要 ×2）。
- `POINTS["all_channels"]=(973,1004)` 是金刚区第二页 `desc="全部频道"` 节点的中心，节点识别失败时作为坐标兜底。
- Web 平台请保持 **单个** `python app.py` 实例：Windows 下多个进程可同时绑定 5000 端口，会把 SSE 日志分流到不同进程，导致页面看到的日志不完整。改完代码要重启 Web 服务才会生效。
- **弹窗没有【去浏览】就立即刮卡**：`task1_seckill.py` 主循环每轮先检查当前屏有没有【去浏览】，没有就直接跳出收尾，不再逐屏滚动空转；`MAX_SCAN_SWIPES` 由 8 降为 2；`JDUI.first_scratch_button()` 优先返回当前屏第一条【去刮卡】，边回滚边找、找到即点。实测同一场景从「弹窗空转约 4 分钟」缩短到 20 秒内。

### 多轮刮卡 + page_source 提速（2026-11-11）

- **刮完一张不代表结束**：实测点击【立即刮卡】后 1 秒内「可抵」金额就上涨（如 47.74→47.76），但主按钮**仍然是【立即刮卡】**——页面自动切到下一张待刮卡，10 秒后也没变回【做任务解锁刮卡】。旧版 `wait_scratch_done()` 死等按钮变回解锁态，在多卡场景下必然超时。现在改用 **`wait_balance_change()`：以「可抵金额变化」判到账**；余额不变就左滑【任务卡】换一张，连续无进展即退出，避免原地死点。
- **【任务卡】是横向轮播**：`SWIPES["task_cards"]=(900,620)->(200,620)`，左滑后主按钮可能从【做任务解锁刮卡】变成【立即刮卡】。`JDUI.swipe_task_cards()` 封装该动作。
- **外循环**：`_consume_cards()` 刮完当前所有卡 → `refresh_beans_page()` 返回上一页再重进天天领豆 → `unlock_button()` 检查【做任务解锁刮卡】→ 有则重新【全部任务】浏览 + 第一条【去刮卡】，再刮一轮；无则结束。带 `MAX_CARD_ROUNDS` 与 `idle_rounds` 双重刹车，防止任务重置导致无限循环。
- **`waitForIdleTimeout=500` 是关键提速**：天天领豆是持续动画的 H5 页，UiAutomator 默认等 10s 空闲，实测每次 `page_source` 要 10~21s（XML 57KB）。调到 500ms 后约 2s，调到 100ms 约 1s；XML 长度与全部关键节点完全一致，只是不再干等动画结束。对比：默认 21.58s / 2000→4.75s / 500→2.00s / 100→0.86s。
- **page_source 短 TTL 缓存**：`JDUI.source()` 缓存 0.8s，把同一时刻的多次判断（按钮 / 余额 / 页面状态）合并成一次 dump；`tap` / `swipe` / `back` / 冷启动 / 直接 `driver.swipe` 都会 `invalidate()`，轮询余额时强制取新 XML。
- 实测 `allowInvisibleElements=False` 只把 XML 从 57KB 降到 38KB，**耗时不变**（仍约 20s），且有丢节点风险，故保留 `True`。
- **Appium 未启动 / adb 掉线时不再只报 `Message:`**：`utils/driver.py` 新建 session 前先探 4723 端口，不可达或创建失败会抛带排查建议的中文错误；`task1_seckill.py` 把 `get_driver()` 纳入 `try`，`ui` 未创建时也不会二次异常吞掉根因。设备 `offline` 会导致 Appium session 整体失效，需重新插拔 USB / 在手机上确认 USB 调试授权后，重启 Appium 与 Web 服务。

### 刮卡循环补漏 + Web 平台实跑验收（2026-11-11）

- **发现一个会漏刮卡的缺陷**：旧版 `_consume_cards()` 里连续 2 次「点击【立即刮卡】后可抵金额未变化」就整轮 `break`，此时屏幕上【立即刮卡】其实还在。`_web_verify3_log.txt` 第 1 轮 09:27:44 / 09:27:59 两次未到账后直接收尾（本轮 0 张）；而第 2 轮 09:29:46 未到账后左滑，09:29:56 就成功刮到新卡（53.10→53.11）。**一次未到账只说明这一张卡失效，不代表没有下一张卡**。
- **修复**：`MAX_NO_CHANGE` 2→4，未到账后继续左滑并尝试下一张卡；只有连续 4 次都未到账才停止点击、改为「只左滑找新卡」，`MAX_SEARCH_SWIPES=3` 后收尾。真正的收敛条件仍是**连续 2 次左滑都看不到【立即刮卡】**（`MAX_EMPTY_SWIPES`），另用 `MAX_CARD_CLICKS=30` 兜底。重试时到账轮询 8s→5s，避免在失效卡上干等。
- **离线回归**（`_test_card_search.py`，不连手机）：E「未到账→左滑→下一张卡到账」必须刮到 1 张（旧逻辑为 0 张）；F「按钮常在且余额不变」4 次点击后 3 次左滑内退出；G「3 张正常卡」逐张刮完。原有 A/B/C 多轮循环与 D 点击失效守卫同步复测通过。
- **Web 平台端到端验收**（`_web_verify3_log.txt`，`run_id=74e195f8`，09:24:41→09:30:32）：`POST /api/run/秒杀任务` 触发，冷启动 → 金刚区第二页【全部频道】→【优惠权益】→【秒杀】→【赚更多京豆】→【全部任务】，完成 **7 个【去浏览】**、**2 次刮卡**（53.09→53.10→53.11），刷新后检测到**没有【做任务解锁刮卡】**才 `[done]`，全程无 `error`、无新增 `debug_shots` 错误截图。说明是命中了任务要求的真实终止条件，不是被 `MAX_CARD_ROUNDS` / `idle_rounds` 刹车拦下。
- **补丁后复跑**（`_web_verify4_log.txt`，`run_id=9de1e7d3`，09:48:34→09:49:57）：`[done] 秒杀任务完成：浏览 0 个任务、刮卡 2 次`，可抵 53.12→53.13→53.14，收敛条件同样是「刷新后没有【做任务解锁刮卡】」。本次京东尚未补发【去浏览】任务，所以走的是「弹窗无浏览 → 直接第一条【去刮卡】」快速路径（1 分 43 秒完成），没有 `error`。注意：这次真机未复现「点击未到账」分支，该分支由离线用例 E 覆盖。
- 验收后 USB 曾掉线导致 Appium 进程退出（`adb.exe: device ... not found`），属环境问题：`adb kill-server && adb start-server && adb reconnect offline` 后设备恢复 `device`，重启 Appium（`--session-override`）与单实例 Flask 即可继续跑，不需要用户手动关闭京东。

## 任务2【东东农场】完整流程

在 Web 页面点击「东东农场」卡片即可（等价于 `POST /api/run/东东农场`）：

1. **入口**（`modules/task2_farm.py` → `FarmUI.open_farm`）：冷启动京东 → 金刚区第一页、左滑后的第二页都按 `content-desc="东东农场"` 扫节点，命中即点；两页都没命中才走兜底【全部频道】→【互动游戏】→【东东农场】
2. 农场页等右侧气泡渲染 → 点【抽10京豆】进入【农场幸运转盘】
3. 逐个点击【逛一逛】，进入浏览页停留 **15 秒** 后返回；循环到整张任务列表里数不到【逛一逛】（即全部变成【继续逛】）
4. 点【开始抽奖】，直到按钮下方的【剩余N次】变成 0

模块参数在 `modules/task2_farm.py` 顶部：`BROWSE_SECONDS=15`、`FARM_WAIT=18`、`WHEEL_WAIT=15`、`MAX_BROWSE_TASKS=40`、`MAX_SCROLLS=20`、`MAX_NO_PROGRESS=3`、`MAX_EMPTY_SCROLLS=3`、`MAX_DRAWS=40`、`MAX_DRAW_NO_PROGRESS=3`。

> 停留秒数的演变：页面文案写的是 `6s` → 实测 7s 仍不计数（不加抽奖次数）→ 2026-11-12 定 10s → **2026-11-13 定 15s**。原因是点【逛一逛】后要先进【抽奖】入口再进转盘页，**入口和转盘加载本身要吃掉几秒**，10s 里净浏览时间不够，任务会不计数。所以这里不是 `X+4`，而是按「净浏览时间够不够」实测定的固定 15s。

### 入口怎么找最方便（2026-11-11 实测结论）

需求里提了两条路，实测之后**两条都用节点定位：主路径优先 + 兜底**，不是二选一：

| 路径 | 步骤 | 定位方式 | 评价 |
| --- | --- | --- | --- |
| 金刚区两页 | 首页 →（必要时左滑一次）→ 点【东东农场】 | 原生节点 `content-desc="东东农场"`，可点击 | **主路径**：最短；精确定位不受个性化排序、位置变化影响，无需标定坐标 |

### 入口（需求原文）

XML 里这张卡的文案是 **【更多任务】**（Button `[22,821][225,1113]`），
【领更多】只是卡内底部的小按钮文字，所以入口按
`ENTRY_TEXTS = (更多任务, 领更多, 天天领豆)` 三级兜底，点在卡片下缘（`y2-48`）。

### 可做任务的判据（严格按需求字面）

一行必须**同时**满足：

1. 奖励小字含【完成得Y京豆】（实测 `浏览完成得2京豆` / `完成得2京豆`）；
2. 右侧按钮 ∈ `{去浏览, 逛一逛, 去完成}`。

按这个判据天然排除：`完成任务获得抽奖机会` + 【去完成】、`浏览6S获得抽奖机会`、
`享券后超低价`、`SK-II洗面奶13.9元限时抢`、`晚8加码 至高8.8元` —— 哪怕按钮也叫【去完成】。

### 做任务与循环

点按钮 → 停留 `random 9~10` 秒 → `back` 一次回面板；回不来就再 back / 重建入口。
循环扫描到**整张任务列表没有可做任务**为止（不是固定次数）。

### 真机踩的 9 个坑

1. **任务面板根本不进无障碍树（今天最关键的发现）** —— 面板打开时
   `page_source` 里既没有【做任务得奖励】也没有【去完成】，但截图里弹窗好好的；
   `classify()` 只能判成 `center`。所以 **OCR 是主力通道，不是兜底**：
   `MAX_OCR = 40`，但只在「刚点完入口」的 `OCR_GRACE = 2` 帧里跑（一次 10~15s，见坑 2）。
2. **PaddleOCR 一次 30~45s**（本机实测 45.3s / 30.6s）→ 已优化到 **10~15s**：
   只识别底部面板区 `OCR_BOX = (0, 860, 1080, 2180)` 并降采样到 0.45 倍
   （同图实测 23.4s → 12.7s；**裁到 y≥1030 会把标题裁掉，OCR 认不出【做任务得奖励】**，
   所以上边界必须 ≤ 860）。仍然不能每帧都跑。
3. **面板是底部半屏 sheet，向下拖会把它关掉** —— `scroll_to_top` 首轮直接 return，
   只在真的向上滑过（`panel_scrolled`）之后才回顶。
4. **进度任务要跟到 M/M** —— `逛活动页面领京豆(2/5)` 这种分 5 步的任务，
   用固定「单任务最多 3 次」会停在 (4/5)。改为 `task_limit()`：
   带 `(N/M)` 的跟到 M 次（`MAX_PER_TASK_PROGRESS = 12` 封顶），无进度的才用 `MAX_PER_TASK = 3`。
5. **商品落地页会残留【领券中心】标题** —— H5 在同一 WebView 里换页，
   落地页那帧 XML 还带着底页的 WebView 节点，只按 center 判会对着商品卡点【领更多】的坐标。
   加 `LANDING_MARKS = (条评价, 好评率, 继续浏览, 好物清单)` 优先判 `landing`；
   **不要用【到手价】**（领券中心底页的商品卡里也有）。
6. **入口卡的 y 会漂移** —— 页面偶发多插一行金刚区或更高的券 banner，
   实测同一张卡被顶到 `y≈1685`。`_find_entry` 不再卡 `y 600~1400`。
7. **浮层 X 的 bounds 退化** —— `[1080,337][1068,314]`（y2<=y1）会被 `parse_bounds` 丢掉，
   只能按参考坐标 `(540,2050)` 点白色 X，再 back 兜底。
8. **`去完成` 在 XML 里是 `clickable=false` 的 TextView** —— 按钮判据不能要求 clickable，
   只能靠「弹窗标记 + 可视安全区 + 贴右 x 区间」；弹窗叠在底页之上，两页节点混在一起，
   必须用 `SAFE_TOP=1050 / SAFE_BOTTOM=2168` 圈出可视区（底栏 y≥2169）。
9. **uiautomator2 instrumentation 会崩** —— 真机上多次出现
   `ECONNREFUSED 127.0.0.1:8201` / `socket hang up` / `instrumentation process cannot be
   initialized within 30000ms`。`_revive()` 会用 `utils.driver.get_driver()` 重建 session 续跑；
   但崩到 `instrumentation` 起不来时只能人工恢复：
   `adb shell am force-stop io.appium.uiautomator2.server` 后重启 Appium。

### 已知边界（别当成已验收）
